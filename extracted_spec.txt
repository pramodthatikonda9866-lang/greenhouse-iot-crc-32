6. CRC-32 Validation Flow
CRC-32 is the core error-detection mechanism. It produces a 32-bit value derived from the packet payload. The
receiver independently calculates CRC-32 and compares it with the value carried by the packet.
Sender: generate reading → build payload → calculate CRC-32(payload) → attach CRC → transmit.
Transmission: copy packet unchanged or modify it according to the configured corruption rule.
Receiver: read packet → separate payload and transmitted CRC → recalculate CRC-32 → compare → VALID or
CORRUPTED.
VALID example:
Received CRC    = 8F3A21C7
Calculated CRC  = 8F3A21C7
Result          = VALID
CORRUPTED example:
Received CRC    = 8F3A21C7
Calculated CRC  = 2B91D440
Result          = CORRUPTED
Important: CRC-32 detects accidental data changes; it is not encryption, authentication, or a method for repairing
corrupted data.

9. Reliability Metrics
The reliability engine aggregates packet results into metrics that can be understood during a project demonstration.
Packet Reliability (%) =
    Valid Packets / Total Received Packets × 100
Error Rate (%) =
    Corrupted Packets / Total Received Packets × 100
Corruption Rate (%) =
    Corrupted Packets / Total Generated Packets × 100

13. Error, Empty & Reliability States
Empty: “No simulation data yet — configure the test and start a run.” Do not display misleading 100% reliability when
there are no packets.
Running: show live packet counts and an active indicator.
Completed: show final generated, received, valid, corrupted, lost, reliability, and highest-error sensors.
Simulator/backend failure: show a clear error and stop/pause safely; do not silently display stale results.
CRC mismatch: mark the packet CORRUPTED and retain the received payload and CRC information for analysis.

14. Reliability & Validation Rules
• CRC-32 input must be deterministic and identical at generation and verification time.
• Store transmitted/original CRC and recalculated CRC separately.
• A CRC mismatch always produces CORRUPTED.
• A CRC match means the packet passed the CRC check; it does not prove physical correctness or authenticity.
• Keep packet loss separate from CRC corruption if loss simulation is enabled.
• Every run must have a unique run ID.
• Reset must clearly separate old statistics from the new run.
• Handle empty datasets without division-by-zero or misleading metrics.
Test
Expected behavior
0% corruption
All received packets pass CRC-32
5% corruption
Approximately the configured fraction is corrupted
100% corruption
All altered packets fail CRC-32
One-field modification
Modified packet fails CRC-32
No data
Dashboard shows empty state
Reset
Counters and packet list return to initial state

16. Demo Script — What “Done” Looks Like
1. Open dashboard; show idle state.
2. Configure 101 sensors, packet count, and a corruption probability such as 5%.
3. Start simulation; show live packet generation and CRC-32 values.
4. Show a VALID packet where transmitted and recalculated CRC-32 values match.
5. Show a CORRUPTED packet where the payload changed and CRC values differ.
6. Show reliability and corrupted-packet counters updating.
7. Open Sensor Analysis and identify high-error sensors.
8. Complete the run and show final statistics.
9. Change corruption rate and run again to demonstrate different reliability behavior.
Final project definition: A software-based IoT communication reliability and data-integrity monitoring system that
simulates 101 sensors, uses CRC-32 to detect simulated packet corruption, and visualizes reliability through a web
dashboard.
